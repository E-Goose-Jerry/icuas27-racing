# 踩坑与教训

写法约定（学自团队另一套栈的故障记录格式）：**现象 → 根因 → 验证过的修法**。
只写真正踩过的，不写「理论上可能」的。新坑按时间顺序追加。

---

## 1. 官方 19 个 Race 航点不是门中心

**现象**：把 `session.yml` 里 `Race` 面板的 19 个航点当作 7 个门中心，
生成赛道后发现第 4、5 号门水平距离 0.52 m、高度差 3.35 m，
推出来的门朝向也自相矛盾（一个朝 -170°，下一个朝 +33°）。

**根因**：那组点是**飞行路径点**，中间夹着为绕开障碍、调整高度插入的过渡点；
「7 个唯一位置」只是恰好等于门的数量（规则书也是 7 个门），容易误导。

**修法**：保留为 `provisional_sample`，字段里写明 `yaw_source: "estimated"`，
并在 `docs/03-赛道与门.md` 记录推不出的原因。真实朝向等场馆公布或现场量。

**教训**：**数量凑巧相等不等于语义相同**。数据来源要写到能追到具体行号。

## 2. `crazyflie_map` 世界里**有** 7 个门框（此条先前写错，已更正）

**先前的错误结论**：说那个 world 里只有 7 个 0.2–0.6 m 的小障碍箱、没有门。

**实际**：`base_crazyrun` 是地面，`obstacles_crazyrun` 就是规则书里那 **7 个 1 m × 1 m 的门框**。
Gazebo 起来后 `/get_model_list` 就三个模型：`base_crazyrun`、`obstacles_crazyrun`、`uav1_crazyflie_0`，
渲染出来的画面是清楚的 7 个门框（`docs/shots/gazebo-arena.png`）。

**错在哪**：我把 OBJ 的 `o Cube*` 分组当成"一个物体"，算出每组包围盒 0.19–0.6 m 宽就觉得不是门。
其实**每个分组只是门框的一根立柱或横梁**，整扇门由同一组的多段几何拼成。

**教训**：**别用单个组件的包围盒判断"物体是什么"**，框架/薄板类网格尤其会骗人。
判断地图里有什么，要么渲染出来看，要么按空间邻接把杆件聚合成整体再量。

详见 `docs/03-赛道与门.md`；门框的真实位姿可以直接从这个网格解析出来。

## 3. `Vec3.from_any` 不吃自己吐出来的 dict

**现象**：125 个测试里有 20 个报 `could not convert string to float: 'x'`
—— 全都发生在「`Gate.to_dict()` → `Gate.from_dict()`」这条往返上。

**根因**：`to_dict()` 产出 `{"x":..,"y":..,"z":..}`（给 JSON 用），
但 `from_any()` 只接受 `Vec3` 或 list/tuple，于是遍历 dict 时拿到的是键名 `"x"`。

**修法**：`from_any` 增加 `Mapping` 分支，缺 `z` 时默认 0。
往返测试因此覆盖了「序列化后再读回来必须相等」这条契约。

**教训**：**序列化/反序列化必须成对测试**。一个 20 个测试同时失败的 bug，
根因往往只有一个，先看共性再逐个修。

## 4. `pkill -f` 把自己的 shell 杀了

**现象**：想停掉后台的地面站进程，执行
`pkill -f "ground_station.server --port 8791"` 后，命令没有输出、
整条 bash 调用被 SIGTERM 终止，后面的编辑也没执行。

**根因**：`pkill -f` 匹配的是完整命令行，而**执行这条命令的 shell 自己的命令行里就包含这个字符串**，
所以它先匹配到了自己。

**修法**：用方括号打断自匹配：`pkill -f "ground_station[.]server"`；
或者按 PID 精确杀、用 `pkill -x <comm>`（comm 截断到 15 字符）。

**教训**：工作区 `AGENTS.md` 里早就写了这条，我还是踩了。
**「杀进程」这类操作要先想「这个模式会不会匹配到我」。**

## 5. 测试装进包之后 `unittest discover` 报 not importable

**现象**：`python3 -m unittest discover -s tests -t .` 报
`ImportError: Start directory is not importable`。

**根因**：`-t .` 把项目根设为顶层，`tests/` 就必须是一个包（有 `__init__.py`）。

**修法**：`tests/__init__.py` 加一行 docstring。ROS 包里那边用 `pytest test`，不需要。

## 6. 测试类名不匹配 pytest 默认规则，一条都没收集到

**现象**：`python3 -m pytest test -q` 输出 `no tests ran`，但文件里明明有 22 个测试。

**根因**：pytest 默认只收集 `Test*` 开头的类；我按 unittest 习惯写成了 `IntrinsicsTest`（后缀式）。

**修法**：类名改成 `TestIntrinsics` 等。保留了 `unittest` 风格的方法名，两边都能跑。

**教训**：**「测试通过了」和「测试跑了」是两件事**。看到 `no tests ran` 要去改，不能当成成功。

## 7. 陈旧数据预算是「平台选择」，不是「自动探测」

**现象**（来自团队另一套无人机栈的记录，本项目沿用）：
SITL 里 PX4 心跳 1 Hz，但仿真倍速会把「1 秒一次」变成墙上时钟的 1/倍速；
用真机的 1 s 预算，健康链路会被判成失效，安全逻辑反复误停。

**修法**：`SafetyLimits` 里 sim / real 两套值，由 `platform` 参数**显式**选择，
未知值一律回落到 real（更严）。**不做自动切换** —— 自动切换会在最需要确定性的时刻改变阈值。

**教训**：安全阈值宁可显式配置错，也不要隐式猜对。

## 8. 看板如果可写，就是个事故源

**现象**：设计地面站时第一反应是加「起飞」「急停」按钮。

**根因**：浏览器标签页、公网端口、误触、刷新重放 —— 任何一个环节都能让无人机在没有确认的情况下动。

**修法**：看板**只读**；操作走 `ros2 service call`，页面上把命令原样印出来让人复制。
`race_control` 服务本身有状态校验（`start` 只在 IDLE 有效），重复调用不会重复起飞。

**教训**：**「谁能下命令」这件事，能少一个入口就少一个。**

## 9. 采样点正好落在门平面上 → 过门被丢掉，下个门被记成漏门

**现象**：看板显示 `gate 1 missed (lateral +0.51 m, vertical -0.30 m)`，进度一直是 0/21。
更怪的是：飞行器明明从门中间穿过去了。

**根因**（三个叠在一起）：

1. `crossing()` 里「起点在平面上 → 没有方向 → 不算穿越」。
   但**我们瞄准的航点就是门心**，所以「采样点正好落在平面上」是常态，不是边界情况。
   丢弃这一次之后，下一段从平面出发也算不出方向 → 整次过门消失。
2. `direction` 还是按 `along_start < 0` 判断。起点在平面上时 `along_start == 0`，
   于是被判成 `direction = -1`（反向穿门）→ 状态机重试同一扇门。
3. 记忆只在「当前帧」更新。平面那一帧两侧都不是，记忆断掉 → 下一帧也不知道自己刚从哪边来。

**修法**：

- `crossing()` 新增 `start_side` 参数，并且 `direction` 改用「记住的来向」而不是原始坐标。
- `RaceMission` 维护 `_target_side`：每帧用非零侧更新；记忆为空时**从上一帧补种**。
- 落点离门心太远（> `capture_radius`，默认 2.5 m）的穿越判为「路过」，不算尝试、不罚时。
- 副作用：过门判定**晚一个采样周期**判定（30 Hz 下约 30 ms），这是正确的 ——
  站在平面上的那一瞬间确实不知道你要往前还是往后。

**教训**：**"恰好落在边界上"不是罕见情况，当你的目标点就是那个边界时它就是主路径。**
三个 bug 叠在一起，症状却只有一个，所以修的时候要一次把整条链走通，
不能看到「能过门了」就收手。

## 10. 回放器把「航点到达」判早了，看起来像是控制逻辑坏了

**现象**：修完过门 bug 后，速度 6 m/s 时 14/14 全过，速度 2 m/s 时第一次过门就报 `lateral +0.51`。
看起来像「低速时过门判定有问题」。

**根因**：在 `MockRace._advance()` 里，我用了跨 tick 累加的 `_seg_progress` 去和
**每 tick 重算的剩余距离** `length` 比较：

```python
self._seg_progress += step            # 累加，跨 tick 不清零
if self._seg_progress >= length:      # length 却是"这一 tick 的剩余距离"
    self._segment += 1
```

`length` 每 tick 都在变小，累加值却在变大 → 航点在还有半米的时候就宣布到达，
于是路径从「先到进门前 1.2 m 再穿门心」变成斜着切过去，切到了门框外面。

速度 6 m/s 时单步 1.5 m 大于段长，恰好掩盖了它；2 m/s（单步 0.5 m）就暴露。

**修法**：删掉累加器，用「这一步是否吃完了剩余距离」判断到达（`step >= length - 1e-9`），
并补了一个 2 m/s 跑完整圈的回归测试。

**教训**：**两个量必须同一基准才能比较。** 一个是累积历史、一个是瞬时剩余，
不等式两边的时间语义不同。另外：**换参数值重跑一遍**能暴露只在特定步长下出现的 bug ——
这次是「用 6 m/s 测完就以为通了」。

## 11. 手抄官方安装脚本，漏掉了三件要命的事

**现象**：为了避开 `install.sh` 的交互式提问，我写了一版"等价"的 `bootstrap_lus.sh`
（clone → `gitman install --group px4 --group simulation` → 覆盖 crazyflie → `colcon build`）。
看起来步骤齐全，实际漏了三样东西。

**根因**（读完 `install.sh` 全部 233 行才发现的）：

| 漏掉的 | 后果 |
|---|---|
| `gitman install simulation px4 --force`（**组名是位置参数，没有 `--group`**） | 第一步就报错退出 |
| `laser_uav_simulation/scripts/build_px4_firmware.sh` | PX4 SITL 二进制是**单独构建**的，不是 colcon 包；没有它 `px4_api.launch.py` 起不来 |
| Micro-XRCE-DDS-Agent（cmake + `sudo make install`）+ acados（NMPC 求解器） | uXRCE-DDS 通信断、`control_manager` 找不到求解器 |
| 还有：一批 apt/pip 依赖（mavlink、pcl、ceres、`empy==3.3.4`、kconfiglib）、`GAZEBO_*`/`LD_LIBRARY_PATH`、逐包 symlink | 编译报错或运行时找不到模型/插件 |

**修法**：**不手抄，改为驱动官方脚本自带的 CI 非交互分支**：

```bash
export GITHUB_ACTIONS=true GITHUB_WORKSPACE=/opt REAL_UAV=false FCU=px4
./install.sh          # CI 分支：read -p 全部跳过，gitman install simulation px4 --force
```

`install.sh` 里本来就写着 `if [ "${GITHUB_ACTIONS}" == "true" ]` 的分支，
是主办方给 CI 用的、被测试过的路径。把仓库放在 `$GITHUB_WORKSPACE/git/laser_uav_system`、
设好 `FCU=px4` 就能全自动跑完（含 PX4 固件、DDS Agent、acados、环境变量、colcon build）。

**配套的两个坑**：

- `install.sh` 结尾有 `source ~/.bashrc`，而它在 `set -e` 下。
  我在 Dockerfile 里往 `.bashrc` 追加的那行如果是 `[ -f x ] && source x`，
  文件不存在时返回 1 → **整个安装脚本中止**。必须写成 `if [ -f x ]; then ...; fi`。
- `docker build` 在**启动那一刻**就把 Dockerfile 和上下文快照了。
  构建过程中改文件，对正在跑的那次**无效**，必须 Ctrl+C 重跑（已完成层会命中缓存）。

**教训**：**"等价实现"是个陷阱。** 上游脚本里每一行都在解决一个你不知道的问题；
非交互需求应该去找上游自己的开关（CI 分支、环境变量），而不是重写一遍。
判断方法是：`grep -n "GITHUB_ACTIONS\|CI\|--non-interactive" install.sh`。

## 12. `gazebo11` 在 Ubuntu 22.04 官方源里不存在

**现象**：`docker build` 在 ROS 那一层挂掉：

```
E: Unable to locate package gazebo11
E: Unable to locate package libgazebo11-dev
ERROR: failed to build: ... exit code: 100
```

**根因**：`gazebo11` / `libgazebo11-dev` 是 **OSRF 源**（`packages.osrfoundation.org`）的命名。
Ubuntu 22.04 (jammy) 自己的 universe 源里，Gazebo Classic 11 就叫 **`gazebo`** 和 **`libgazebo-dev`**（版本号是 `11.10.2+dfsg-1`）。
22.04 之前的发行版两个名字都有，所以网上抄来的 Dockerfile 经常写错。

**修法**：改成 `gazebo libgazebo-dev`。验证方式不是靠猜，是先花两分钟 dry-run：

```bash
docker run --rm ubuntu:22.04 bash -c 'apt-get update -qq &&
  apt-get install -s -y --no-install-recommends gazebo libgazebo-dev' | tail -3
```

`apt-cache policy <包名>` 能直接看到候选版本，比翻网页快。

**顺带修的两处**：

- PX4 的 SITL 构建需要 `jinja2`/`toml`/`yaml`/`packaging`，官方 `install.sh` 没装。
  不补的话会在构建到第 20 分钟的 PX4 那一步才炸 —— 补在 ROS 那一层（反正已经失效要重跑）。
- Dockerfile 的 `RUN` **续行里不能写注释**。`RUN a \` + `# 说明` + `  b` 会把 `#` 当参数传给 shell。
  用 `docker build --check` 可以在真正构建前把这类语法问题查出来。

**教训**：**"命令跑完了"不等于"构建成功了"。** 判断成功看产物，不看退出观感：

```bash
docker images | grep icuas27     # 有没有镜像
```

`docker build` 失败时会留下已完成的缓存层，所以 `docker system df -v` 里能看到"有一层 411 MB、很新"——
那不代表成功，只代表**第一层成功了**。

## 13. `.bashrc` 在非交互 shell 里直接 return，导致 colcon 找不到 `ament_cmake`

**现象**：官方 `install.sh` 一路跑到最后一步 `colcon build` 才炸，而且炸得很奇怪：

```
CMake Error at CMakeLists.txt:27 (find_package):
  ... has asked CMake to find a package configuration file provided by
      "ament_cmake", but CMake did not find one.
Failed   <<< realsense2_camera_msgs [0.30s, exited with code 1]
Summary: 0 packages finished [0.76s]
```

一个装了 `ros-humble-desktop` 的镜像，却"找不到 ament_cmake"。

**根因**：`install.sh` 在编译前做的是

```bash
source ~/.bashrc
colcon build ...
```

而 Ubuntu 的 `/root/.bashrc` 第 6 行是：

```bash
# If not running interactively, don't do anything
[ -z "$PS1" ] && return
```

Docker 里是 `bash -c`（非交互）→ `PS1` 为空 → **`.bashrc` 立刻 return，里面那条
`source /opt/ros/humble/setup.bash` 根本没执行** → colcon 在裸环境里跑 → 挂在第一个消息包上。

**修法**：在调用 `install.sh` **之前**由我们自己 source：

```bash
source /opt/ros/humble/setup.bash
./install.sh
```

环境变量会被子进程继承，`install.sh` 内部那次 colcon 就能看见 `ament_cmake` 了。
另外把 `install.sh` 的退出码用 `set +e` 接住 —— 它的最后一步就是编译，
就算那次失败，后面我们自己还会再 `colcon build` 一遍，不该因此整体判死。

**紧接着的第二个坑**：加上 `source /opt/ros/humble/setup.bash` 之后构建**秒失败**：

```
/opt/ros/humble/setup.bash: line 8: AMENT_TRACE_SETUP_FILES: unbound variable
```

因为脚本开头是 `set -euo pipefail`，而 **ROS 的 setup 脚本不是 `set -u` 安全的**
（它读一个可能没定义的环境变量）。必须临时关掉：

```bash
set +u
source /opt/ros/humble/setup.bash
set -u
```

**教训**：

1. **"在容器里 `source ~/.bashrc`"基本等于没 source。**
   凡是依赖交互式 shell 初始化的脚本，进容器第一件事是显式 source 你要的那份 setup。
   判断方法：`bash -c 'source ~/.bashrc; echo $AMENT_PREFIX_PATH'`，空的就是中招了。
2. **`set -u` 和第三方 setup 脚本天生不和**。凡 source 别人的环境脚本，前后各加一句
   `set +u` / `set -u`，否则错误信息会指向对方的文件，让人以为是他写错了。
3. **两个坑叠在一起时，第一个修复会立刻暴露第二个** —— 所以修完别急着提交，
   先用最小复现跑一遍（这里是 1 秒的失败，代价小；要是跑到 25 分钟才暴露就贵了）。

## 14. `REAL_UAV` 必须是带引号的字符串 `"false"`，写成 `false` 会静默走真机分支

**现象**：镜像构建"成功"跑过了 gitman、跑过了 acados，然后在 `colcon build` 里挂：

```
--- stderr: livox_ros_driver2
CMake Error at CMakeLists.txt:64 (find_library):
  Could not find LIVOX_LIDAR_SDK_LIBRARY ...
Failed   <<< livox_ros_driver2 [10.8s, exited with code 1]
```

而且事后检查发现 **PX4 的 SITL 固件根本没编译**（`px4_sitl_default` 在日志里 0 次命中，
`ros_packages/px4_firmware/build/` 整个不存在）。

**根因**：`install.sh` 的分支判断是

```bash
FALSE="\"false\""                      # CI 分支里：值是 7 个字符，含引号
if [ "$REAL_UAV" == $FALSE ]; then     # 然后这样比
```

我们按常规设 `REAL_UAV=false`（5 个字符）→ 比较不相等 → **走 else，也就是真机分支**：

| 真机分支的后果 | 证据 |
|---|---|
| `gitman install real` 装了 18 个真机驱动包（Livox / RealSense / OpenVINS / FAST-LIO） | `.gitman/` 下 18 个目录 |
| **PX4 固件编译是「只在仿真分支」的步骤 → 被整段跳过** | 日志里没有 `px4_sitl_default` |
| 这些驱动反过来要求 Livox SDK（只有真机分支才装）→ colcon 编译失败 | `Could not find LIVOX_LIDAR_SDK_LIBRARY` |

**怎么确认官方要什么值**：直接读它的 CI workflow，别猜：

```yaml
# .github/workflows/simulation-build-px4.yml
env:
  REAL_UAV: '"false"'    # ← 引号是值的一部分
  FCU: 'px4'
```

**修法**：`export REAL_UAV='"false"'`，并**加一条断言**把这个反直觉的约定钉死：

```bash
if [ "${REAL_UAV}" != '"false"' ]; then
    echo "[x] REAL_UAV must be the quoted string \"false\"" >&2
    exit 1
fi
```

**另外两件事**：

- **`ENV` 的位置会影响缓存**。我把 `REAL_UAV` 从 Dockerfile 顶部挪到了 `lus` stage 开头 ——
  在顶部改一行会让下面所有 apt 层（500+ 包，十几分钟）全部失效；放在 stage 里就只影响之后。
- 这个坑最阴的地方是**它不报错**：分支选错了照样往下跑，只是少了 PX4、多了 18 个用不上的驱动包。
  **只要有一个判断是"字符串比较"而不是"布尔开关"，就一定要在启动时打印出实际取到的值。**

**教训**：读上游 CI 配置比读文档可靠。文档说"仿真模式"，CI 告诉你"仿真模式在代码里的确切写法"。

## 15. 环境变量只在 entrypoint 里生效：Gazebo 插件路径为空 → PX4 拿不到传感器 → 没有里程计

**现象**：headless 冒烟测试前 8 项全过（gzserver、PX4、DDS Agent 都在跑、话题都在），
只有一项失败：**里程计没有数据**。

```
[ok] PX4 SITL process running
[ok] MicroXRCEAgent running
[ok] topic /uav1/hw_api/odometry          ← 话题存在
[fail] no odometry rate (estimation_manager not publishing)
```

PX4 自己的日志停在 `Simulator connected on TCP port 4560.`，之后**什么都不打印、也不报错**。
`ros2 topic info /uav1/fmu/out/sensor_gyro` 显示 `Publisher count: 0` —— PX4 的 uXRCE 客户端根本没发布。

**根因**：`install.sh` 把 Gazebo 的插件/模型路径写进了 `~/.bashrc`：

```bash
export GAZEBO_PLUGIN_PATH=$GAZEBO_PLUGIN_PATH:$BASE_DIR/git/laser_uav_system/ros_packages/px4_firmware/build/px4_sitl_default/build_gazebo-classic
```

而 `.bashrc` **只对交互式 shell 生效**（第 13 条），所以这些变量在 `docker exec` 和 launch 子进程里全是空的：

```
GAZEBO_PLUGIN_PATH=[]      ← 空
GAZEBO_MODEL_PATH=[]       ← 空
```

结果 gzserver 加载不到 PX4 的 IMU/气压插件 → PX4 收不到任何传感器数据 → EKF 不初始化 →
不发布 `vehicle_odometry` → `px4_api` 没有输入 → `/uav1/hw_api/odometry` 永远不出现。
**整条链上没有任何一处报错**，只有"没有数据"。

**修法**：把所有运行环境集中到一个文件，用 `BASH_ENV` 让**每个非交互 bash 自动加载**：

```dockerfile
COPY icuas27_env.sh /opt/icuas27_env.sh
ENV BASH_ENV=/opt/icuas27_env.sh
```

文件里统一设置：ROS、两个工作区、`GAZEBO_PLUGIN_PATH`/`GAZEBO_MODEL_PATH`/`LD_LIBRARY_PATH`、
`ACADOS_SOURCE_DIR`、`PYTHONPATH`、`HOME=/opt`（第 16 条会讲为什么）、`UAV_NAME`/`UAV_TYPE`。

**教训**：

1. **"环境变量放在 .bashrc 里"在容器里等于没有**。要么进 `ENV`，要么进 `BASH_ENV`，
   要么在每个入口显式 source —— 三者选一，别指望 `.bashrc`。
2. **Docker 有四个入口，每个的环境都不一样**：`ENTRYPOINT`、`docker exec`、
   `docker run <cmd>`、以及 launch 起的子进程。只有第一个会走 entrypoint。
   `BASH_ENV` 是唯一能一次覆盖所有的机制。
3. **"话题存在"不等于"有数据"**。`ros2 topic list` 里的话题可能是订阅者创建的；
   判断链路通没通用 `ros2 topic info`（看 publisher count）和 `ros2 topic hz`。
