# 官方 LUS 接口备忘

从 `laser_uav_managers` / `laser_msgs` 的 README 与 msg 定义里提炼的，只留本项目实际用到的。
**官方仓库更新后以官方为准**。

## 起飞前的服务调用顺序

```bash
export UAV_NAME=uav1
ros2 service call /$UAV_NAME/hw_api/arm std_srvs/srv/Trigger {}          # 解锁
ros2 service call /$UAV_NAME/control_manager/takeoff std_srvs/srv/Trigger {}  # 起飞
ros2 service call /$UAV_NAME/control_manager/land std_srvs/srv/Trigger {}     # 降落
ros2 service call /$UAV_NAME/planning_manager/cancel std_srvs/srv/Trigger {}  # 取消规划→保持
```

`race_mission` 会自动调这四个；`cancel` 同时被用作「急停保持」。

## 本项目用到的输入

| 话题 | 类型 | 用途 |
|---|---|---|
| `/<uav>/estimation_manager/estimation` | `nav_msgs/Odometry` | 唯一的位置来源（过门判定的输入） |
| `/<uav>/camera/ai_deck/image_raw` | `sensor_msgs/Image` | 前视相机（mono8 324×244 @30Hz） |
| `/<uav>/camera/ai_deck/camera_info` | `sensor_msgs/CameraInfo` | 内参（有就用，没有用默认近似值） |

## 本项目发出的输出

| 话题/服务 | 类型 | 说明 |
|---|---|---|
| `/<uav>/planning_manager/trajectory_path` | `laser_msgs/TrajectoryPath` | 每扇门 3 个航点（进门前 1.5 m / 门心 / 出门后 1.5 m） |
| `/icuas27/race_control` | `icuas27_interfaces/RaceControl` | start / abort / safe_stop / reset |
| `/icuas27/race_status_json` | `std_msgs/String` | 完整 JSON 契约 |
| `/icuas27/race_status` | `icuas27_interfaces/RaceStatus` | 精简状态（给不喜欢 JSON 的订阅者） |

## 轨迹消息怎么填

```msg
bool stop_on_waypoints                 # 竞速时永远 false
float64 speed                          # 这段航点的目标速度 m/s
laser_msgs/PoseWithHeading[] waypoints # position(x,y,z) + heading(rad)
```

关键点：

- `stop_on_waypoints: false` —— 否则每扇门前都会减速停一下，竞速直接废掉。
- `heading` 填门的朝向（`gate.yaw`），让机头对准门心，前视相机才有画面。
- **速度上限不是这里决定的**，是 `laser_uav_planners/params/agile_planner/crazyflie.yaml`
  里的 `max_vel: 3.0` / `max_accel: 14.0`。这里的 `speed` 只是期望值。

## 规划器选型

| 后端 | 包 | 用途 |
|---|---|---|
| **PMM** | `pmm_planner` | **时间最优**，竞速用这个（`planner: pmm`） |
| MINCO | `super_planner` | 平滑最小 snap，官方默认 |
| SUPER | `super_planner` | 带避障/重规划，需要 `laser_uav_mappings` + 点云 + TF |

改选型只改 `planning_manager` 的 yaml（`sim/configs/planning_manager.yaml`），
**运行中不能切**，要重启规划管理器。

## 控制管理器要点

- 外环 100 Hz，INDI 内环 250 Hz。
- `reference.timeout: 0.50` —— 参考轨迹超过 0.5 s 没更新就判失效。所以任务节点发完航点后
  **不能长时间沉默**；`race_mission` 的 10 Hz 状态发布不负责喂轨迹，只有过门时发新航点。
  如果一段航点要飞很久（>0.5 s 正常），规划器自己会持续发 `reference_horizon`，
  任务节点不需要重复发。**这一点必须在仿真里确认**，见下。
- `goal.position_tolerance: 0.45` m、`goal.heading_tolerance: 3.15` rad。

## ⚠️ 待仿真确认的三件事

1. **航点发一次够不够**：PMM 生成一次轨迹后会一直发布 `reference_horizon` 直到完成，
   但如果任务节点发新航点时旧轨迹还没飞完，行为是什么（覆盖？排队？）需要看实测。
2. **`autostart.py` 会不会自己 arm**：官方 session 里有个 `autostart` 脚本，
   会和我们的 `start` 命令抢解锁时序，第一次跑要盯日志。
3. **Crazyflie 的 AI-deck 画面**：`--enable_ai_deck` 是否真的产出 `image_raw`，
   以及曝光/帧率对检测的影响，只能看实际画面。
