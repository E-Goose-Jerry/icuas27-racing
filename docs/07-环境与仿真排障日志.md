# 环境构建与仿真排障日志

这份文档按**时间线**记录搭建仿真环境过程中遇到的每一个问题，格式统一为
**现象 → 根因 → 修法 → 验证方式**。目的有三个：

1. 下次重建镜像时不用重新踩一遍（每个坑都标了"落在哪个文件的哪一行"）；
2. Phase 1 提交需要"构建说明 + 非交互启动"，这份日志就是它的原始素材；
3. 队友接手时能看懂"为什么这里要这么写"——很多写法看起来多余，其实每一行都对应一次失败。

> 逻辑层（竞赛规则、状态机、计时）的教训在 [`05-踩坑与教训.md`](05-踩坑与教训.md)；
> 这份只讲**环境与仿真**。

| 轮次 | 耗时 | 死在哪一步 | 根因 | 修法 |
|---|---|---|---|---|

## 1. `gazebo11` 包名在 Ubuntu 22.04 上不存在

**现象**

```
E: Unable to locate package gazebo11
E: Unable to locate package libgazebo11-dev
ERROR: failed to build: ... exit code: 100
```

**根因**：`gazebo11` / `libgazebo11-dev` 是 **OSRF 源**的命名。
Ubuntu 22.04 (jammy) 自己的 universe 源里，Gazebo Classic 11 叫 `gazebo` 和 `libgazebo-dev`。
22.04 之前的发行版两个名字都有，所以网上抄来的 Dockerfile 经常写错。

**修法**：`sim/docker/Dockerfile` → `gazebo libgazebo-dev`。

**验证**（不用等整轮构建，两分钟）：

```bash
docker run --rm ubuntu:22.04 bash -c 'apt-get update -qq &&
  apt-cache policy gazebo libgazebo-dev | grep -A1 "gazebo"'
# Candidate 应该是 11.10.2+dfsg-1
```

**顺带**：PX4 的 SITL 构建要 `jinja2`/`toml`/`yaml`/`packaging`，官方 `install.sh` 不装。
不补的话会在构建到第 20 分钟的 PX4 那一步才炸，所以一并放进 ROS 那一层。

## 2. `.bashrc` 在非交互 shell 里直接 return → colcon 找不到 `ament_cmake`

**现象**

```
CMake Error at CMakeLists.txt:27 (find_package):
  ... has asked CMake to find a package configuration file provided by
      "ament_cmake", but CMake did not find one.
Failed   <<< realsense2_camera_msgs [0.30s, exited with code 1]
Summary: 0 packages finished
```

一个装了 `ros-humble-desktop` 的镜像却"找不到 ament_cmake"。

**根因**：`install.sh` 编译前做的是 `source ~/.bashrc; colcon build ...`，
而 Ubuntu 的 `/root/.bashrc` 第 6 行是：

```bash
# If not running interactively, don't do anything
[ -z "$PS1" ] && return
```

Docker 里是 `bash -c`（非交互）→ `PS1` 为空 → **`.bashrc` 立刻 return**，
里面那句 `source /opt/ros/humble/setup.bash` 根本没执行。

**修法**：`sim/docker/bootstrap_lus.sh` 在调用 `install.sh` 之前自己 source：

```bash
set +u
source /opt/ros/humble/setup.bash
set -u
```

**验证**：

```bash
docker run --rm icuas27-racing:local bash -c 'echo "[$AMENT_PREFIX_PATH]"'
# 非空才对
```

## 3. `set -u` 与 ROS 的 setup 脚本冲突（构建秒失败）

**现象**：加上 source 之后立刻报

```
/opt/ros/humble/setup.bash: line 8: AMENT_TRACE_SETUP_FILES: unbound variable
```

**根因**：脚本开头是 `set -euo pipefail`，而 ROS 的 setup 脚本会读一个可能未定义的环境变量，
`-u` 把它变成致命错误。**错误信息指向 ROS 的文件，很容易误以为是对方写错了。**

**修法**：source 前后关/开 `-u`（`bootstrap_lus.sh` 两处：install 前、最终 colcon 前）。

**教训**：凡 source 第三方环境脚本，前后各加一句 `set +u` / `set -u`。

## 4. `REAL_UAV` 必须是带引号的 `"false"`，裸 `false` 会静默走真机分支

**现象**：构建"顺利"跑过 gitman、跑过 acados，然后在 `colcon build` 挂：

```
--- stderr: livox_ros_driver2
CMake Error at CMakeLists.txt:64 (find_library):
  Could not find LIVOX_LIDAR_SDK_LIBRARY ...
```

而且事后发现 **PX4 的 SITL 固件根本没编译**（日志里 `px4_sitl_default` 0 次命中，
`ros_packages/px4_firmware/build/` 不存在）。

**根因**：`install.sh` 的判断是

```bash
FALSE="\"false\""                    # CI 分支：值是 7 个字符，引号是值的一部分
if [ "$REAL_UAV" == $FALSE ]; then   # 这样比
```

我们设 `REAL_UAV=false`（5 个字符）→ 不相等 → **走 else，也就是真机分支**：

| 真机分支的后果 | 证据 |
|---|---|
| `gitman install real` 装了 18 个真机驱动（Livox / RealSense / OpenVINS / FAST-LIO） | `.gitman/` 下 18 个目录 |
| **PX4 固件编译只写在仿真分支里 → 整段跳过** | 日志里没有 `px4_sitl_default` |
| 这些驱动要求 Livox SDK（也只有真机分支会装）→ colcon 失败 | `Could not find LIVOX_LIDAR_SDK_LIBRARY` |

**怎么确认官方要什么值**：读它的 CI workflow，别猜：

```yaml
# .github/workflows/simulation-build-px4.yml
env:
  REAL_UAV: '"false"'    # ← 引号是值的一部分
  FCU: 'px4'
```

**修法**（两处相反，都要保留）：

| 位置 | 值 | 谁需要 |
|---|---|---|
| `bootstrap_lus.sh`（构建期 export） | `'"false"'`（带引号） | `install.sh` 的 `[ == $FALSE ]` |
| 镜像 `ENV REAL_UAV`（运行期） | `false`（裸值） | `px4_api.launch.py` 里的 `PythonExpression('"' + REAL_UAV + '" == "false"')` |

**踩到的第二层**：我一开始把镜像 ENV 也设成带引号的，结果运行时 launch 直接挂：

```
[ERROR] Caught exception in launch: invalid syntax (<string>, line 1)
```

因为表达式拼成了 `""false"" == "false"`，是 Python 语法错误。

**防御**：`bootstrap_lus.sh` 里加断言，值不对立刻退出：

```bash
if [ "${REAL_UAV}" != '"false"' ]; then
    echo "[x] REAL_UAV must be the quoted string \"false\", got [${REAL_UAV}]" >&2
    exit 1
fi
```

**教训**：**"字符串比较"型的开关，一定要在启动时打印实际取到的值**——
分支选错不报错，只是少了 PX4、多了 18 个用不上的驱动包。

## 5. 环境变量只在 entrypoint 里生效 → Gazebo 插件路径为空 → 没有里程计

**现象**：headless 冒烟测试前 8 项全过（gzserver、PX4、DDS Agent 在跑，话题都在），只有一项失败：

```
[ok]   topic /uav1/hw_api/odometry          ← 话题存在
[fail] no odometry rate (estimation_manager not publishing)
```

PX4 日志停在 `Simulator connected on TCP port 4560.` 之后什么都不打印、也不报错。

**根因**：`install.sh` 把 Gazebo 插件/模型路径写进了 `~/.bashrc`：

```bash
export GAZEBO_PLUGIN_PATH=...:$BASE_DIR/.../px4_firmware/build/px4_sitl_default/build_gazebo-classic
```

而 `.bashrc` **只对交互式 shell 生效**（第 2 条）。于是 `docker exec` 和 launch 子进程里这些变量是空的：

```
GAZEBO_PLUGIN_PATH=[]      ← 空
GAZEBO_MODEL_PATH=[]       ← 空
```

结果：gzserver 加载不到 PX4 的 IMU/气压插件 → PX4 收不到传感器数据 → EKF 不初始化 →
不发布 `vehicle_odometry` → `px4_api` 没有输入 → `/uav1/hw_api/odometry` 永远不出现。
**整条链上没有任何一处报错。**

**修法**：把所有运行环境集中到一个文件，用 `BASH_ENV` 让**每个非交互 bash 自动加载**：

```dockerfile
COPY icuas27_env.sh /opt/icuas27_env.sh
ENV BASH_ENV=/opt/icuas27_env.sh
```

`sim/docker/icuas27_env.sh` 里统一设置：ROS、两个工作区、`GAZEBO_PLUGIN_PATH`/`GAZEBO_MODEL_PATH`/
`LD_LIBRARY_PATH`/`GAZEBO_RESOURCE_PATH`、`ACADOS_SOURCE_DIR`、`PYTHONPATH`、`HOME=/opt`、
`UAV_NAME`/`UAV_TYPE`。

**为什么 `BASH_ENV` 而不是 `ENV`**：Docker 有四个入口，环境各不相同 ——
`ENTRYPOINT`、`docker exec`、`docker run <cmd>`、以及 launch 起的子进程。
只有第一个会走 entrypoint，`BASH_ENV` 是唯一能一次覆盖所有的机制。

**验证**：

```bash
# 判断链路通没通要看 publisher count，不能只看话题存不存在
ros2 topic info /uav1/hw_api/odometry          # Publisher count > 0
ros2 topic hz     /uav1/estimation_manager/estimation   # 应约 100 Hz
```

## 6. LUS 脚本写死 `~/git/laser_uav_system`，`HOME` 必须是 `/opt`

**现象**（第一个可视版本的失败）：

```
[spawn_drone_uav1-1] Error: Unable to open file[/tmp/laser_uavs_description/sdf/crazyflie_0.sdf]
[spawn_drone_uav1-1] line 24: cd: /tmp/git/laser_uav_system/ros_packages/laser_uav_simulation/ROMFS/: No such file or directory
```

**根因**：`spawn_drone.sh` 里路径是字面量的 `~/git/laser_uav_system/...`。
我为了文件权限把容器 `HOME` 指到了 `/tmp`，于是它去 `/tmp/git/...` 找东西。

**修法**：运行态 `HOME=/opt`（因为 LUS 装在 `/opt/git/laser_uav_system`）。
这一条写在 `icuas27_env.sh` 里，注释说明了原因。

## 7. 容器里跑 root 还是宿主机 UID：两个方向都有坑

**现象 A**（跑 root）：`docker exec` 里编译，产物在宿主机上是 root 所有，普通用户删不掉：

```
rm: 无法删除 'ros2_ws/build/COLCON_IGNORE': 权限不够
```

**现象 B**（跑 UID 1000）：PX4 起不来 —

```
[spawn_drone_uav1-1] Error getting username: no matching password record.
```

**根因**：镜像里没有 uid 1000 的 passwd 记录，PX4/Gazebo 查用户失败；
而 root 写进 bind mount 的文件宿主机用户改不了。

**修法**：**分开两种用途**——

| 用途 | 用户 | `HOME` | 在哪 |
|---|---|---|---|
| 编译（`build-race`） | 宿主机 UID | `/tmp` | `run_sim.sh::run_container_as_user` |
| 运行仿真 | root | `/opt` | `run_sim.sh::run_container` |

## 8. `docker commit` 会丢掉镜像配置（ENTRYPOINT / WORKDIR / ENV）

**现象**：修好镜像后 `docker run --rm img bash -c 'echo $AMENT_PREFIX_PATH'` 输出空 ——
entrypoint 根本没执行。

**根因**：我用 `docker commit --change 'ENV REAL_UAV=...'` 重提交时，
**只带了 ENV 一个 `--change`**，`ENTRYPOINT`/`WORKDIR`/`CMD` 全被重置成默认。

**修法**：每次 commit 都带全四项：

```bash
docker commit \
  --change 'ENV REAL_UAV=false' \
  --change 'ENV BASH_ENV=/opt/icuas27_env.sh' \
  --change 'WORKDIR /opt/icuas27_racing' \
  --change 'ENTRYPOINT ["/opt/entrypoint.sh"]' \
  --change 'CMD ["bash"]' <container> icuas27-racing:local
```

**验证**：

```bash
docker inspect icuas27-racing:local --format 'Entrypoint={{.Config.Entrypoint}} Workdir={{.Config.WorkingDir}}'
```

## 9. `ENV` 写在 Dockerfile 顶部，改一行让 500 多个包重装

**现象**：只改了 `ENV REAL_UAV` 一行，`docker build` 从头开始重装 apt，5 分钟时我自己的超时把它掐了
（`CANCELED`），磁盘白掉 9 GB。

**根因**：`ENV` 在 Dockerfile 顶部 → 它之后的**所有层**缓存键都变了。

**修法**：需要随运行态变化的 `ENV` 放到**最后一个 stage 的开头**（`FROM base AS lus` 之后），
只让后面几层失效。相应的注释也写在那里，说明为什么不在顶部。

## 10. `docker exec` 不跑 entrypoint，冒烟脚本里的 `pgrep -f` 又会匹配到自己

**现象 A**：冒烟脚本里每一步都是 `ros2: command not found`。

**根因**：`docker exec <ctr> bash -c '...'` 不经过镜像的 `ENTRYPOINT`，环境是裸的。
（根治办法就是第 5 条的 `BASH_ENV`；脚本里另外也保留了一段显式 source 作为双保险。）

**现象 B**：`pgrep -f gzserver` 明明 gzserver 没起来却返回成功。

**根因**：`-f` 匹配完整命令行，而**检查命令自己的命令行里就含 "gzserver"**。

**修法**：用 `pgrep -x gzserver`（精确匹配进程名）。

**同类坑**：`pkill -f "python3 -m ground_station.server"` 会把自己的 shell 杀掉 ——
所以要按 PID 杀，或用 `pkill -f "ground_station[.]server"` 打断自匹配。

## 11. 失败一次就烧掉 25 分钟：改成常驻容器迭代

**现象**：`docker build` 的失败层不进缓存，PX4 编译那 15 分钟每次都要重做。
四轮下来光构建就烧了约一小时。

**修法**：把 Dockerfile 拆成两个 stage，先 `--target base` 拿到"只有 apt 层"的镜像
（全部命中缓存，75 秒），再起一个**常驻容器**在里面跑 bootstrap：

```bash
docker build --target base -t icuas27-base:local sim/docker
docker run -d --name lus-build icuas27-base:local sleep infinity
docker cp sim/docker/bootstrap_lus.sh lus-build:/opt/
docker exec lus-build bash /opt/bootstrap_lus.sh        # 失败后容器还在，可断点续跑
docker commit <全四项 --change> lus-build icuas27-racing:local
```

这样 PX4 编完之后即使 colcon 失败，改一行重跑只需要几十秒。

⚠️ **代价**：当前镜像是这样"提交"出来的，**Dockerfile 还没用一次干净构建验证过**。
Phase 1 要求"干净环境按文档能构建"，所以提交前必须补一次完整 `docker build`。

## 12. 可视化：X 授权 → GPU → shader，三层依次暴露

这一步只在**开窗口**时才出现，headless 全程是绿的。

### 12.1 X 授权

```
[gzclient-2] Authorization required, but no authorization protocol specified
[ERROR] gzclient-2: process has died [exit code -6]
```

**根因**：只挂 `/tmp/.X11-unix` 不够，容器还需要 X 的 cookie 文件。
**修法**：挂 `~/.Xauthority`（本机是 `/run/user/1000/gdm/Xauthority`）并设 `XAUTHORITY`。

### 12.2 GPU / GL

```
MESA: error: Failed to query drm device.
libGL error: glx: failed to create dri3 screen
```

**根因**：容器里没有 `/dev/dri`。
**修法**：`--device /dev/dri`（本机 Intel 核显 + NVIDIA 两张卡，传设备即可，不需要 `--gpus`）。
注意 `--group-add render` 会报 `no matching entries in group file`（镜像里没这个组），运行态是 root 就不用加。

### 12.3 `GAZEBO_RESOURCE_PATH` 未设 → shader 找不到 → Camera 断言

前面两层修完后仍然崩，报的是这一条：

```
[Err] [RTShaderSystem.cc:480] Unable to find shader lib. Shader generating will fail.
      Your GAZEBO_RESOURCE_PATH is probably improperly set.
      Have you sourced <prefix>/share/gazebo/setup.bash?
[Err] [RenderEngine.cc:197] Failed to initialize scene
[Err] [GLWidget.cc:177] GLWidget could not create a scene.
gzclient: ... boost::shared_ptr<gazebo::rendering::Camera>::operator->(): Assertion `px != 0' failed.
```

**根因**：`/usr/share/gazebo/setup.bash` 会设 `GAZEBO_RESOURCE_PATH`，而官方安装脚本
只把它写进 `.bashrc`（同第 2 条）。**gzserver 不需要 shader 所以一直是好的，只有客户端会崩**
——这就是为什么 headless 冒烟测试全绿、开窗口就崩。
`: Assertion px != 0` 只是最后的连带症状，不是根因。

**修法**：`icuas27_env.sh` 里加

```bash
if [ -f /usr/share/gazebo/setup.bash ]; then
    source /usr/share/gazebo/setup.bash
fi
```

**验证**：

```bash
docker exec smoke bash -c 'echo $GAZEBO_RESOURCE_PATH'   # 非空
docker exec smoke bash -c 'pgrep -x gzclient'            # 有进程
DISPLAY=:0 xdotool search --name Gazebo                  # 有窗口
```

## 13. 地图里的"那 7 个东西"到底是什么（判断错误）

**现象**：我早期断言 `crazyflie_map` 里没有门、只有 7 个 0.2–0.6 m 的障碍箱，
并把这个结论写进了文档和 `AGENTS.md`。

**实际**：那就是**规则书的 7 个 1 m × 1 m 门框**。渲染出来一目了然
（`docs/shots/gazebo-arena.png`），`/get_model_list` 也确认只有地面 + 障碍 + 无人机三个模型。

**错在哪**：我把 OBJ 的 `o Cube*` 分组当成"一个物体"去算包围盒。实际上**每个分组只是门框的一根立柱或横梁**，
整扇门由同一分组的多段几何拼成，包围盒自然又窄又高。

**后果**：这件事改变了做法 —— 门的真实位姿**可以直接从网格解析**，不必再靠"从飞行航点反推"的估计值。

**教训**：**别用单个组件的包围盒判断"物体是什么"**。框架/薄板类网格尤其会骗人；
要么渲染出来看，要么按空间邻接把杆件聚合成整体，再量尺寸。

## 14.5 第一次真飞：起飞成功，但**轨迹跟踪被 NMPC 卡住**

**做成了什么**：发 `start` 之后 arm → takeoff 生效，飞机确实离地了，计时开始跑，
看板上门进度 0/14、目标门 #1、零罚时。

**⚠️ 但"悬停"这个词是错的**（我最初就是这么误报的，被用户当场指出）：

```
z: 1.21 → 1.19 → 1.19 → 1.13 → 1.06 → 0.74 → 0.69 → -7.7 → -49.6 → -600
```

8 秒内从 1.21 m 掉到 0.69 m，随后彻底发散。**这不是悬停，是起飞机动结束后没有任何控制器接管、
飞机在重力下往下掉**，最后连状态估计都炸了。起飞请求的是 1.5 m，实际只到 1.21 m —— 推力跟踪本身也不准。

**没做成什么**：它**不朝 1 号门飞**。逐层挖下去，是四个问题叠在一起：

| # | 现象 | 根因 | 状态 |
|---|---|---|---|
| 1 | `takeoff: service not ready, request dropped` | 我的节点在**同一 tick** 里先 arm 再 takeoff，那时服务还没被发现，代码把请求**丢掉**了 | ✅ 改成"服务未就绪就排队重试"（尚未提交） |
| 2 | `control_manager` 的 launch 直接抛异常 | `laser_uav_planners` 是"收集仓库"，**没有 `package.xml`**，而 `control_manager.launch.py` 用 `FindPackageShare('laser_uav_planners')` 拼默认参数路径 | ✅ 给它补一个最小 ament 包（`sim/bringup.sh` 里） |
| 3 | 规划器 381 次拒绝 `fresh control state and odometry in the same frame are required` | **上游 launch 漏了 remap**：C++ 里发的是 `control_state_out`，规划器订阅 `control_manager/state`，launch 只映射了 `diagnostics_out` 没映射它 | ✅ 补 remap（`sim/bringup.sh` 里） |
| 4 | 规划器生命周期停在 Configured、不激活 | **启动顺序**：`planning_manager` 必须**在 `control_manager` 之后**起，否则激活静默失败 | ✅ 固化进 `sim/bringup.sh` 的顺序与等待 |
| 5 | 还是飞不动，最后发散 | `control_manager` 报 `SQP_RTI: QP solver returned error status 3`（**3215 次**），`ready_for_tracking` 永远是 false → 规划器拒绝 → 没有参考 → NMPC 更算不出来 | ❌ **未解决** |

第 5 条（NMPC）在控制层查到**两个独立缺陷**，都写在下文 §14.6。

第 5 条是**循环依赖**：

```
NMPC 求解失败 → ready_for_tracking=false → 规划器拒绝航点
   → 控制器没有参考轨迹 → NMPC 更算不出来 → 求解继续失败
```

`control_is_fresh()` 的实现（`planning_manager_node.cpp:588`）明确要求
`control_->ready_for_tracking`，所以这个环闭得很死。

**另一条教训**：`--device /dev/dri` 不是"优化"，是**必需**。加上之前 gzclient 用软件渲染吃
**900% CPU**（9 个核），把 gzserver 挤到物理只剩 1 Hz（`sensor_gyro` 1 Hz、`/clock` 39 Hz）；
加上之后 gzclient 降到 14.8%、`/clock` 恢复到 199 Hz。

## 14.6 控制层检查：为什么飞机掉下来

**结论先行**：不是"悬停调得不好"，是**外环根本没有输出、内环没有反馈**。

### 缺陷 A：INDI 内环拿不到电机转速反馈（上游已知）

`control_manager` 订阅 `/uav1/hw_api/motor_speed_estimated`，类型 `laser_msgs/msg/MotorSpeedStamped`。
实测这个**话题根本不存在**：

```
$ ros2 topic list | grep motor_speed
/uav1/control_manager/motor_speed_reference        ← 只有指令，没有反馈
```

上游自己的 README 写明了原因：

> Motor-speed feedback also needs matching message types: this PX4 API publishes
> `MotorSpeed`, while `control_manager` subscribes to `MotorSpeedStamped`.
> **A topic remapping alone cannot connect those types.**

即：PX4 仿真路径下 `px4_api` 发的是**不带时间戳**的 `MotorSpeed`，而 `control_manager`
要 `MotorSpeedStamped`。**类型不兼容，remap 救不了**。结果 INDI 的 `motor_speed_estimated_`
恒为 0，drag/thrust 估计失效。

### 缺陷 B：NMPC（acados）从第一次求解就失败

```
SQP_RTI: QP solver returned error status 3 QP iteration 10.
multirotor_ode_acados_solve() failed with status 4.
```

单次运行 **3215 次**。`status 3` = 达到最大迭代（不可行/未收敛）。

后果是死循环：

```
NMPC 失败 → ready_for_tracking=false
        → planning_manager 拒绝一切航点（control_is_fresh() 要求 ready_for_tracking）
        → 控制器没有参考轨迹
        → NMPC 更算不出来
```

`planning_manager_node.cpp:588`：

```cpp
return control_ && control_->ready_for_tracking && control_->flight_id != 0 && ...;
```

### 相关参数（供调参参考）

| 项 | 值 | 备注 |
|---|---|---|
| 机体质量 | `0.025 kg` | 25 g，数值尺度很小 |
| 惯量 | `[1.66e-5, 1.67e-5, 2.93e-5]` | — |
| 推力常数 `c_thrust` | `1.28e-8` N/(rad/s)² | — |
| NMPC 权重 | `Q=[40, 20, 0.3, 1.0, 0.3, 0.3]`、**`R=1000`** | R 比 Q 大 25–3000 倍，对 25 g 机体偏病态 |

| 控制模式 | `individual_thrust` + INDI | px4_api **只支持这个模式**（它没订阅 `attitude_rates_and_thrust`） |

### 起飞机动本身也没达标

请求 `takeoff height 1.5 m`，日志写 `Takeoff requested: z 0.001 -> 1.500, duration 2.81s`，
实际只到 **1.21 m** 就开始下沉 —— 与缺陷 A（推力估计失效）一致。
